# Development guide

## Manual setup

Run from the repository root. Python 3.11+ and Node 22.12+ are required; no paid services are needed.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
cp backend/.env.example backend/.env        # only if you do not already have a local file
cp frontend/.env.example frontend/.env.local
cd frontend && npm ci && cd ..
```

In two terminals:

```bash
# Terminal 1, repository root
.venv/bin/uvicorn backend.main:app --host 0.0.0.0 --port 8080 --reload --no-access-log

# Terminal 2
cd frontend
npm run dev
```

On Windows, substitute `.venv\Scripts\python.exe -m pip`, `.venv\Scripts\python.exe -m uvicorn`, and PowerShell `Copy-Item` commands. `run_local.ps1` and `run_local.bat` wrap the normal setup without deleting data. Native Windows execution was not tested in the review environment.

The frontend is on port 3000. `BACKEND_URL` is read by its server-side proxy; **do not** add a browser `NEXT_PUBLIC_BACKEND_URL=http://localhost:8080`. A remote user's browser has a different localhost.

### Local data

Development applies Alembic migrations at startup, then opens `backend/data/workspace.db`. Never point tests at a live database. Do not copy v1 `mock_db.json` into this path. See [Migration](MIGRATION.md).

To start a clean throwaway workspace **without deleting the current one**, choose a new SQLite filename in `DATABASE_URL`, or create an isolated demo account. If you deliberately remove a database, stop the server and back it up first, including its WAL state. There is no automatic destructive reset script.

### Real Vertex AI

Use `gcloud auth application-default login` locally and the settings in [Configuration](CONFIGURATION.md). Install no service-account JSON file in the repository. The default mode remains explicit demo until changed. `AI_MODE=disabled` supports testing the manual application while AI is unavailable.

## Quality workflow

```bash
.venv/bin/ruff check backend
.venv/bin/ruff format --check backend
.venv/bin/pytest --cov=backend --cov-report=term-missing
.venv/bin/python -m backend.scripts.export_openapi

cd frontend
npm run lint
npm run typecheck
npm run format:check
npm test
npm run build
npx playwright install --with-deps chromium
npm run test:e2e
```

`npm run format` fixes frontend formatting. `ruff format backend` fixes Python formatting. Generated Alembic revisions are excluded from broad lint rewrites; inspect and format migrations explicitly.

Playwright normally launches a dedicated API on 8081 and UI on 3001, an ignored `.cache/e2e.db`, and `.next/e2e` build output. It does not reuse or delete your normal workspace database. `E2E_BASE_URL` can target another **disposable demo-enabled** instance; do not use it against production. `PYTHON_BINARY` and `PLAYWRIGHT_EXECUTABLE_PATH` support alternative local installations.

Browser traces/screenshots can contain account/workspace content. Test against generated data and keep these ignored artifacts private.

## Database migrations

```bash
.venv/bin/alembic upgrade head
.venv/bin/alembic current
.venv/bin/alembic check
# After intentionally changing a model:
.venv/bin/alembic revision --autogenerate -m "Describe the schema change"
```

Review autogenerated SQL/types/indexes and test both databases. Never rely on `create_all` as a production migration mechanism. The test suite deliberately uses it for most isolated tests and separately exercises real upgrade/check/downgrade/upgrade behavior.

## Dependency updates

Python `.in` files express maintained ranges; `.txt` files are the installable compiled pins. After an intentional upgrade:

```bash
.venv/bin/pip-compile --resolver=backtracking --strip-extras -o backend/requirements.txt backend/requirements.in
.venv/bin/pip-compile --resolver=backtracking --strip-extras -o backend/requirements-dev.txt backend/requirements-dev.in
.venv/bin/pip install -r backend/requirements-dev.txt
.venv/bin/pip-audit -r backend/requirements.txt
```

For JavaScript, update through npm and commit **both** manifests and the lockfile. Run `npm ci` to prove reproducibility and `npm audit` to inspect advisories. Do not commit `node_modules`, `.next`, virtualenvs, credentials, local databases, or test traces.

ESLint is pinned to 9.39.5 because the checked Next/React plugin failed against ESLint 10's removed context API. This is a tooling compatibility constraint, not an excuse to ignore future advisory updates. Upgrade once the combined lint stack passes. Dependency audits are point-in-time checks, not a security guarantee.

## Contributing and scope

Respect the existing restrictive [license](../LICENSE) and maintainer permission requirements. For authorized changes:

1. Write a regression test for the behavior you are fixing.
2. Keep API changes reflected in typed frontend contracts and generated OpenAPI.
3. Preserve tenant scoping, parameterized queries, explicit errors, CSRF, and version checks.
4. Never let an LLM directly mutate records or execute arbitrary tools.
5. Describe any paid integration, migration, destructive operation, or new data recipient clearly.
6. Include mobile, keyboard, loading, empty, error, and dark-mode states in UI changes.
